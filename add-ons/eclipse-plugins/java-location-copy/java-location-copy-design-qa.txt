Q1. このプラグインの設計は、ドメイン駆動設計に即していますか。

A. DDDの要素はありますが、全体としてはレイヤー分割を採用した設計です。
DDDに反しているわけではありませんが、domainパッケージがあるだけでDDDになる
わけでもありません。

DDDに沿っている点:
・TypeLocation / MethodLocation が、扱う概念をモデルとして表現しています。
・ドメイン層がEclipse APIに依存していません。
・UI操作と位置情報の変換・整形を分離しています。

一方、モデルは主にデータを保持し、規則はSelectionValidatorやProcessorに
置かれています。「有効なJava位置情報とは何か」「どの選択をコピー対象とするか」
という契約も、モデルの生成時には保証されません。
ドメインのルールをモデル中心に表現するという点では限定的です。

DDDに寄せるなら、クラスを増やすよりも次の仕様を明確にすることが先です。
・コピー対象は宣言名だけか、メソッド内の選択も含むか。
・行番号は宣言行か、選択開始行か。
・有効な位置情報に必要な値は何か。

そのうえで、位置情報モデルに必須値や行番号の検証を持たせ、Eclipse固有の
選択解析を外側で処理すると境界が明確になります。
小規模で複雑な業務ルールも少ないため、DDDを全面的に導入する必要性は低く、
現在の責務分離を維持してモデルの契約を明確にする程度が規模に合っています。

Q2. 設計意図をより明確化するために、どこを改善できますか。

A. 選択の仕様と、各層が保証することを明確にするのが最も効果的です。

1. 選択と行番号の意味を決める
   宣言名だけを対象にするか、行番号を宣言行と選択開始行のどちらにするかを
   明記します。現在は文字列の一致で検証し、選択開始行を出力しています。
   仕様に合わせて検証方法と名前を揃えます。

2. アプリケーションの入口を一つにする
   Factory.create(...).buildClipText() より、例えば
   JavaLocationTextBuilder.build(...) とすると、選択からコピー用文字列を作る
   ユースケースが直接伝わります。処理種類を増やす予定があれば、内部で現在の
   Processor構成を維持してもよいです。

3. 引数の型で前提を示す
   Factoryには ISelection ではなく ITextSelection を渡します。
   Mapperには MethodSelection 全体ではなく必要な行番号だけを渡すと、
   変換に必要な情報が明確になります。

4. モデルに有効性を保証させる
   生成時に必須値の非nullと正の行番号を検証し、「生成できた位置情報は
   整形できる」という契約にします。空のパッケージ名は許容します。

5. 名前を処理の意味に揃える
   buildClipText → buildClipboardText、clip → clipboardText、
   cu → compilationUnit が候補です。選択開始行を使う仕様なら、
   lineNumberも selectionStartLineNumber に揃えます。

6. 短い設計文書を置く
   README.mdに入力・出力例、対象外の選択、各層の責務、正式なビルド手順を
   書きます。コメントには「なぜこの仕様・構成にしたか」を残すと有効です。

各要素が保証すること:
・Handler: Eclipseから入力を受け取り、コピー・通知します。
・アプリケーション処理: 選択仕様に従って検証し、処理を組み立てます。
・Mapper: JDT要素を位置情報モデルへ変換します。
・位置情報モデル: 必須情報と行番号が有効であることを保証します。
・Formatter: 決められた形式で文字列を生成します。

まず選択仕様の明文化、引数型の修正、命名の統一から着手すると、構成を大きく
変えずに設計意図を伝えやすくなります。

Q3. この設計の完成度はどれくらいですか。

A. 小規模なプラグインとして7割程度という評価です。
厳密な指標ではなく、責務・契約・保守性から見た主観的な目安です。

・責務分離: 良好。UI・変換・モデル・整形が分かれています。
・依存関係: 良好。ドメイン層がEclipse APIに依存していません。
・命名: おおむね良好。Clip、行番号の意味などに曖昧さが残ります。
・モデルの契約: 改善余地あり。必須値・行番号の有効性を保証していません。
・選択仕様: 改善余地あり。宣言名の選択と名前の一致が区別されていません。
・設定・配布: 基本は整合。Handler登録は正しいものの、ビルド・実行検証は未実施です。

骨格はできていて、仕様と契約を詰める段階です。大幅な再設計よりも、
コピー対象と行番号の意味の明文化、引数型とモデルによる前提の保証、
対象Eclipseでのビルド・実行・コピー確認が完成度の向上につながります。
DDDへの忠実さよりも、用途に対して仕様が明確で変更時に壊れにくいことを
評価軸にするのが適切です。

Q4. 骨格の組み方は適切ですか。

A. 小規模なEclipseプラグインとして、おおむね適切です。
Eclipse固有の処理を外側に置き、位置情報モデルと整形を独立させている点は
良い構成です。ただし分割の粒度には改善余地があります。

・Handler・Mapper・位置情報モデル・Formatter
  それぞれ変更理由が異なるため、分離を維持する価値があります。
・Factory・TypeProcessor・MethodProcessor
  短い一連の処理が複数クラスに分散しています。処理種類を増やす予定がなければ、
  一つのアプリケーションサービスにまとめる方が追いやすくなります。
・TypeSelection・MethodSelection
  独自の規則や振る舞いが少なく、独立したクラスにする利点は現時点では小さめです。

推奨する骨格:

Handler
  → アプリケーションサービス: 選択検証・処理の組み立て
      → Mapper: JDT要素から位置情報へ変換
      → Formatter: 位置情報を文字列へ整形
  → クリップボードへの書き込み・通知

作り直す必要はありません。責務の境界を維持し、処理を追うためだけに経由する
クラスを減らすと、規模に合った骨格になります。

Q5. この設計を簡潔に言い表すとしたら何ですか。
    そして既存アーキテクチャのどれに一番近いですか。

A. 「Javaの選択位置を検証し、位置情報へ変換・整形してコピーする、
小規模なレイヤード設計」です。

既存アーキテクチャでは、レイヤードアーキテクチャ（階層化アーキテクチャ）に
最も近いです。
・プレゼンテーション層: Handlerが入力・コピー・通知を担当します。
・アプリケーション層: Factory / Processor / Mapperが処理を組み立てます。
・ドメイン層: 選択・位置情報のモデル、検証、整形を担当します。

ドメイン層をEclipse APIから独立させる点には、クリーンアーキテクチャに
通じる考え方もあります。ただし外部機能をポートとアダプターで抽象化する
構成ではないため、「ドメインを独立させたレイヤードアーキテクチャ」が
最も実態に合う表現です。

Q6. このプラグインの実装を既存アーキテクチャで実現する場合、
    どんなアーキテクチャでどのように作るのが一番マッチしますか。

A. 薄いアプリケーションサービスを中心にしたレイヤードアーキテクチャです。
現在の骨格を活かし、処理を組み立てる部分を簡素化する構成が規模に合います。

各要素の作り方:
・CopyJavaLocationHandler
  Eclipseから選択を取得し、サービスを呼び、コピー・通知します。
・JavaLocationTextBuilder
  選択を検証し、型・メソッドで分岐して変換・整形を呼びます。
・JavaLocationMapper
  JDT要素を TypeLocation / MethodLocation に変換します。
・位置情報モデル
  必須値と行番号の有効性を生成時に保証します。
・JavaLocationFormatter
  決められた出力形式で文字列を生成します。

処理の流れ:

Eclipseの選択
  → Handler
  → JavaLocationTextBuilder
      → 選択の検証
      → Mapper → 位置情報モデル
      → Formatter → コピー用文字列
  → Handlerでコピー・通知

現在の実装からなら、JavaLocationProcessorFactory、TypeProcessor、MethodProcessor
の処理を JavaLocationTextBuilder にまとめます。TypeSelection / MethodSelection
も独自の規則がなければ統合するか、必要な値を直接渡す形にできます。

Eclipse固有の選択解析は外側、位置情報の有効性と整形はEclipseに依存しない
内側に置きます。JDTに依存するMapperはドメイン層の外に維持します。
本格的なヘキサゴナルアーキテクチャやクリーンアーキテクチャは、別IDEへの
対応や複数の出力先が必要になった段階で検討するとよいです。
現在はレイヤード構成で責務と処理の流れを明確にするのが最も扱いやすいと考えます。
この構成は提案であり、実装済みの変更ではありません。

質疑応答から整理した改善方針

・DDDの形式的な導入より、選択仕様とモデルの契約を優先します。
・UI、JDT変換、位置情報、整形の責務分離を維持します。
・FactoryやProcessor、選択モデルの統合は、今後の拡張予定に応じて判断します。
・命名と短い設計文書で、前提と判断理由を伝えます。
・最終的な完成度は対象Eclipseでの動作検証を含めて判断します。
